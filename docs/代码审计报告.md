# CTF-BTFly 代码审计报告

> 审计日期：2026-07-25  
> 审计范围：项目手写 Go、TypeScript/React、CSS、PowerShell、Taskfile 与 Dockerfile  
> 审计方式：静态代码审阅、数据流/状态机分析、路径与权限边界分析、自动化测试及生产构建验证

## 1. 审计结论

CTF-BTFly 的总体分层清晰：Wails/React 桌面端只负责操作与展示；独立 Go daemon 持有 SQLite、Docker 权限、任务状态和真实模型密钥；每个题目在独立容器中运行 Pi RPC Agent。事件采用“SQLite 持久化 + WebSocket 实时广播 + sequence 断线重放”，模型凭据采用“上游真实 Key 留在 daemon + 容器只拿题目短期 Token”，这是当前实现中最重要的两个正确安全设计。

本轮没有改动业务行为，只补充了中文块级注释和审计文档。原因是审计发现涉及状态机、容器隔离、文件系统边界和数据清理策略，需要在确认产品取舍后分项修复，不能混入纯注释改动。

主要风险集中在：

1. Docker 隔离运行时不可用时会降级到 `runc`，但容器仍可联网、使用 root、拥有可写根文件系统；
2. 附件写入只做词法路径校验，未校验已有父目录符号链接；
3. daemon 异常重启后没有恢复或校正持久化任务状态；
4. 并发启动、终态直接启动和启动中间失败缺少完整状态机保护；
5. 模型 SSE、事件日志和工作区缺少总量/配额边界；
6. 父任务删除不会同步清理隐藏的专项子任务及其工作区。

## 2. 总体架构与数据流

```text
CTF-BTFly.exe
Wails v3 桌面壳
        │ 原生绑定：GetDaemonConnection / PrepareExit
        ▼
React 19 + TypeScript + TanStack Query
        │ Bearer Token REST / 查询参数 Token WebSocket
        ▼
ctfagent-daemon
Go + chi + coder/websocket
        ├── SQLite：任务、事件、模型用量
        ├── EventHub：实时事件广播
        ├── Model Gateway：短期任务 Token → 上游真实 Key
        └── Docker SDK：创建题型专项 Pi 容器
                    │ JSONL stdin/stdout
                    ▼
              Pi Agent RPC
                    │
                    ├── /workspace/attachments
                    ├── /workspace/artifacts
                    ├── /workspace/WRITEUP.md
                    └── 受控专项子任务协作（最多 3 个，可选任一题型）
```

关键执行链：

```text
用户创建题目
→ POST /api/tasks
→ agent.Service.CreateTask
→ SQLite tasks + task.created
→ 上传附件到任务工作区
→ POST /start
→ 签发短期模型 Token
→ Docker 创建专项容器
→ stdin 发送 Pi Prompt
→ stdout JSONL 标准化为平台事件
→ SQLite 持久化后由 EventHub/WebSocket 广播
→ Pi 写入 artifacts 与 WRITEUP.md
→ agent.settled
→ 提取“最终 Flag”章节
→ 前端展示结果与报告
```

## 6. 审计发现

### [高] A-01：runc 降级场景仍允许高能力联网容器

**位置：** `internal/sandbox/manager.go` 的 `Health`、`Start`

普通题找不到 gVisor 时、Pwn 找不到 Kata 时都会自动回退 `runc`。与此同时，容器配置为：

- `User: "root"`；
- `ReadonlyRootfs: false`；
- `NetworkMode: "bridge"`；
- 映射 `host.docker.internal:host-gateway`；
- 任务工作区为宿主机 bind mount；
- Pwn 额外增加 `SYS_PTRACE`。

虽然已经移除其他 capabilities、启用 `no-new-privileges`、限制内存/CPU/PID，runc 仍不等同于 gVisor/Kata 的额外隔离层。面对恶意附件、未知二进制或被 Prompt/工具输出影响的 Agent 时，风险显著。

**建议：**

1. 默认把 `runc` 降级改为显式用户确认或直接拒绝高风险题型；
2. 上线 Linux Worker 后强制 gVisor/Kata，不允许静默降级；
3. 增加 egress allowlist/proxy，默认禁止访问宿主网关非模型端口；
4. 评估以非 root 用户运行，按题型精确增加能力；
5. 为可写层和 bind 工作区增加磁盘配额。

### [高] A-02：附件目标未检查已有符号链接

**位置：** `internal/agent/service.go` 的 `StoreAttachments`、`resolveAttachmentPath`

`resolveAttachmentPath` 只验证规范化后的字符串仍位于 `attachments/` 下，没有解析目标父目录中已经存在的符号链接。`os.MkdirAll` 和 `os.OpenFile` 会跟随已有链接。

任务处于 `paused`、`settled`、`failed` 或 `cancelled` 时允许再次上传附件；其中暂停或已结束但仍保留容器的任务，容器有机会先在 bind 工作区创建链接。随后用户上传同路径文件时，宿主 daemon 可能跟随链接写到预期目录之外。实际影响取决于 Docker Desktop/宿主文件系统的符号链接语义和 daemon 用户权限。

**建议：**

1. 写入前逐段检查父目录，拒绝任何符号链接；
2. 使用支持 `openat`/`O_NOFOLLOW` 或安全 join 的实现；
3. 将 `paused` 也纳入附件锁定状态，或先关闭容器再允许修改；
4. 新增“预置符号链接 + 上传”的回归测试。

### [高] A-03：daemon 异常重启后缺少任务/容器状态恢复

**位置：** `internal/daemon/run.go`、`internal/sandbox/manager.go`、`internal/agent/service.go`

活跃 Session、题目 Token、`settled` 和 `paused` 标志只保存在内存中。daemon 异常退出后：

- SQLite 可能仍显示 `running`、`provisioning` 或 `paused`；
- Docker 容器可能仍存在；
- 新 Manager 没有对应 Session；
- `Abort`、`Resume` 无法找到会话；
- `CloseSandbox` 因任务不是终态而拒绝；
- daemon 安全退出检查会一直被陈旧任务阻塞。

**建议：**

1. daemon 启动时按 `com.ctfagentpi.managed` 标签枚举容器；
2. 将 SQLite 状态与容器真实状态对账；
3. 能重新 Attach 时恢复会话，不能恢复时明确标记 `failed/recovery_required`；
4. 提供管理员“强制回收陈旧实例”接口；
5. 添加崩溃重启集成测试。

### [高] A-04：工作区、事件和 stderr 缺少总量配额

**位置：** `internal/agent/service.go` 的 `readRPC`、`readStderr`；`internal/storage/sqlite.go`；`internal/api/server.go`

已有单条边界包括：

- JSON 请求 2 MiB；
- 上传请求 2 GiB；
- Pi 单条 stdout 事件 16 MiB；
- stderr 单行 2 MiB；
- 文件预览 1 MiB。

但没有任务级或全局总量限制。Agent 可以持续写工作区、输出 stderr/工具事件，SQLite 也没有事件保留或压缩策略。资源限制不包含 bind mount 磁盘配额，可能耗尽宿主磁盘并影响所有任务。

**建议：**

1. 设定单任务工作区、附件、Artifact 和事件总量配额；
2. 对高频增量事件批量合并或设置保留策略；
3. stderr/协议错误只保存截断摘要，完整内容写 Artifact；
4. 监控数据库/WAL/工作区大小并在 UI 告警；
5. 为上传加入任务剩余配额校验。

### [中] A-05：并发与终态启动缺少服务端状态机锁

**位置：** `internal/agent/service.go` 的 `Start`

`Start` 只拒绝 `running`、`provisioning`、`paused`，因此直接 API 调用可以对 `settled/failed/cancelled` 任务调用 Start，而不先走 `Retry → CloseSandbox`。旧容器仍存在时会发生容器名称冲突。

此外，两个并发 Start 请求可能都在读取到 `ready` 后继续执行。当前互斥锁只保护内存 map，不保护完整状态转换。

**建议：**

1. `Start` 只接受 `ready`；
2. 终态重新执行强制走 Retry；
3. 为每个 taskID 增加状态转换锁或数据库条件更新；
4. 使用 `UPDATE ... WHERE status = 'ready'` 的受影响行数实现 CAS；
5. 添加并发 Start 测试。

### [中] A-06：启动中间失败可能遗留 Token 和 provisioning 状态

**位置：** `internal/agent/service.go` 的 `Start`

容器创建成功后，如果把状态更新为 `running` 的 SQLite 操作失败，代码会停止并删除容器，但没有：

- 撤销刚签发的模型 Token；
- 删除 `s.tokens[taskID]`；
- 将任务从 `provisioning` 更新为 `failed`；
- 发送失败事件。

**建议：** 把启动过程实现为带统一 defer 回滚的状态事务；任何中间失败都撤销 Token、清理内存 map、删除容器、落 `failed` 并发出事件。

### [中] A-07：取消任务后短期模型 Token 继续有效

**位置：** `internal/agent/service.go` 的 `Abort`

Abort 只向 Pi 发送 `{"type":"abort"}` 并把任务标记为 cancelled，不停止容器，也不撤销模型 Token。设计上这是为了保留实例供检查，但容器内其他进程仍可能持有 Token 并继续调用模型网关，直到用户手动关闭实例或删除任务。

**建议：**

1. 取消时立即撤销模型 Token；
2. 若需要恢复，应在明确的 Resume/Retry 流程中重新签发；
3. 或者区分“暂停当前回合”和“取消并保留只读实例”两种语义。

### [中] A-08：删除父任务不会清理隐藏专项子任务

**位置：** `internal/storage/sqlite.go` 的表结构与 `DeleteTask`；`internal/agent/service.go` 的 `Delete`

`tasks.parent_task_id` 只是文本字段，没有指向父任务的外键。删除用户可见父任务时，只删除父工作区和父任务行：

- 子任务行仍留在 SQLite；
- 子任务工作区仍留在磁盘；
- 子任务本身被根任务列表隐藏；
- 子任务模型用量在父任务不存在后无法正常归并显示。

**建议：**

1. 增加自引用外键及明确的级联策略，或在服务层事务中列出并删除所有子任务；
2. 清理父任务前先关闭/删除子容器和子工作区；
3. 对历史孤儿任务提供一次性迁移清理。

### [中] A-09：SSE 未完成行缓冲没有大小上限

**位置：** `internal/modelgateway/gateway.go` 的 `usageCaptureBody.capture`

普通 JSON 响应最多捕获 8 MiB，但 SSE 的 `ssePending` 会持续追加，直到遇到换行。恶意或异常上游若发送超长无换行数据，可让 daemon 内存持续增长。

**建议：** 为单条 SSE 行设置上限；超过上限后停止 usage 捕获但继续原样代理响应，并记录一次诊断事件/日志。

### [中] A-10：宽松 CORS 与 WebSocket Origin 依赖“仅本机 + Token”假设

**位置：** `internal/api/server.go` 的 `cors`、`taskEvents`

HTTP CORS 使用 `Access-Control-Allow-Origin: *`，WebSocket 使用 `OriginPatterns: ["*"]`。默认监听 `127.0.0.1` 且所有平台接口需要随机 Token，因此当前风险被显著缓解；但如果用户把 `CTF_DAEMON_ADDRESS` 改为非回环地址，攻击面会扩大。

**建议：**

1. 启动时拒绝非回环监听，除非显式启用远程模式；
2. Wails 场景限制允许的 Origin；
3. 远程模式使用 TLS、独立强认证和来源白名单；
4. 避免把长期 Token 放入可记录的 URL，WebSocket 可改用首条消息认证。

### [中] A-11：镜像供应链缺少不可变校验

**位置：** `images/*/Dockerfile`

Node/Python 基础镜像没有固定 digest，APT 包未固定版本，pip 虽固定版本但未校验 hash，Pi 由 npm 在线安装。构建时间不同可能得到不同系统包，镜像源或依赖发布链被污染时也缺少完整性保障。

**建议：**

1. 固定基础镜像 digest；
2. 在可维护范围内固定系统包快照；
3. pip 使用带 hash 的 requirements lock；
4. npm 使用 lockfile/离线制品并校验完整性；
5. CI 生成 SBOM、执行镜像漏洞扫描和签名。

### [低] A-12：请求与用量解析存在少量健壮性缺口

**位置：** `internal/api/server.go` 的 `decodeJSON`；`internal/modelgateway/gateway.go` 的 `ensureStreamUsage`

- `decodeJSON` 只执行一次 Decode，没有确认请求体后续只剩空白，因此可能接受尾随第二个 JSON 值；
- `ensureStreamUsage` 在 `ReadAll` 返回错误时没有恢复已消费的请求体，极端 I/O 错误下可能把残缺请求转发上游。

**建议：** JSON 解码后再次 Decode 并要求 `io.EOF`；请求体改写前使用可完整恢复的缓冲策略，读取失败时明确返回错误或恢复已读内容。

## 7. 已确认的安全设计

1. daemon 默认只监听 `127.0.0.1`；
2. API Token 使用 `crypto/rand` 生成，比较使用恒定时间函数；
3. 上游真实模型 Key 不进入前端和 Agent 容器；
4. 每次题目启动签发独立短期模型 Token；
5. SQLite 模型账本不保存 Prompt、回复和请求头；
6. 容器不挂载 Docker Socket，不使用 `--privileged`；
7. 默认移除全部 capabilities，仅 Pwn 增加 `SYS_PTRACE`；
8. 启用 `no-new-privileges` 并限制内存、CPU 和 PID；
9. 工作区文件预览会检查目录穿越和解析后的符号链接边界；
10. Flag 只从 Writeup 明确章节的单行代码块提取；
11. 事件先持久化再广播，WebSocket 断线可按 sequence 补齐；
12. daemon 在活跃任务存在时拒绝安全退出。
